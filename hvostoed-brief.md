# «Хвостоед» — бриф проекта для продолжения разработки

Это передаточный документ: вся предыстория, правила, решения и методология мобильной пазл-игры «Хвостоед». К брифу прилагаются файлы: **hvostoed.jsx** — играбельный прототип v3 (React, один файл), **solver.js** — проверка уровней на решаемость, **analyze.mjs** — расширенный анализатор метрик уровня (пространство состояний, вероятности случайной победы, ловушки, ASCII-карты), **gen2.js** — генератор уровней. Задача ассистента, получившего этот документ: разобраться в проекте и продолжать разработку, не ломая зафиксированные здесь правила и рабочие процессы.

## 1. Идея и происхождение

Вдохновение — мобильный пазл **Arrows – Puzzle Escape** (студия Lessmore): тапаешь стрелку, и она вылетает с поля, если путь свободен. Наш твист: вместо стрелок — **змейки, которые едят друг друга за хвост** и растут на длину съеденного. Поле постепенно сворачивается в одну гигантскую змею — это и есть главный кайф.

Рыночная проверка проводилась: прямых аналогов не нашли. Ниша «Snake …» в сторах плотно занята реалтайм-аренами (Snake.io, Snake Clash, Snake Battle и клоны), но это экшены — пошагового детерминированного пазла про поедание за хвост с наследованием направления там нет. Жанрово мы — тап-пазл: зен-темп, короткие сессии, моменты «ага», вертикальный экран, игра одной рукой.

## 2. Ядро правил (точная спецификация)

Поле — сетка W×H. Змея — упорядоченный список клеток, **голова первой**, минимальная длина 2. **Направление взгляда = голова − шея** (вторая клетка); отдельного действия «повернуть» нет, направление меняется только как следствие поедания.

Ход — тап по змее. Из головы бросается луч по направлению взгляда до первого препятствия:

- **чужой хвост** → змея съедает жертву;
- **край поля** (весь путь чист) → змею можно «выпустить» с поля (с подтверждением);
- чужое **тело или голова**, **валун**, **собственное тело**, **хвост колючей** → **авария**: тряска, пунктирный луч, экран поражения с объяснением (см. §3);
- **собственный хвост** → авария («уроборос запрещён»).

**Съедание.** Путь головы = клетки зазора + клетки жертвы от её хвоста к её голове. На каждом шаге голова добавляется вперёд; хвост едока подтягивается **только на не-пищевых клетках** — поэтому рост равен ровно длине жертвы. Едок финиширует на клетке головы жертвы.

**Ключевое эмерджентное свойство:** после съедания едок **наследует направление взгляда съеденной змеи** — он входит в её голову со стороны её шеи, и его новые «голова−шея» совпадают с её прежними. На этом наследовании строится вся глубина планирования цепочек. Это фича №1, её нельзя терять ни при каких изменениях.

**Выпуск.** Змея уползает по прямой за край; её длина теряется навсегда. Это осознанная жертва ради расчистки пути.

**Победа:** хотя бы одна змея длиной ≥ target — неважно, какая именно.

## 3. Fail-states и почему именно так (решение v3)

Лимита ходов больше нет (v2-механика `moves` удалена по решению автора). Поражение наступает в двух случаях:

- **Авария**: тап по змее, чей луч заблокирован (чужое тело/голова, валун, шипы колючей, собственное тело). Змея трясётся, показывается пунктирный луч, через ~0.7 с — экран «Авария!» с объяснением, во что врезалась. Поле при этом не менялось, поэтому кнопка «Продолжить» бесплатно возвращает в игру (философия свободного undo сохранена), «Заново» — рестарт. Смысл: тапы обязаны быть осмысленными, игрок читает направления взгляда (глаза + язычок), ловушки-приманки получают зубы.
- **Тупик**: «Все пути закрыты — двигаться некому» — ни одна змея не может ни есть, ни выпуститься (кнопки «Отменить ход» / «Заново»).

**Undo бесплатен**: мы давим на качество плана, а не на аккуратность пальца. Открытый вопрос-«ручка»: если авария покажется беззубой — убрать «Продолжить» (только «Заново») и/или ввести звезду «без аварий». Отвергнутая альтернатива — **сердечки** за ошибочный тап, как в Arrows: наказывают любопытство дозированно, но размывают ответственность; аварийная модель честнее — не возвращаться к сердечкам.

## 3a. Конец партии: порог — не финиш

Уровень раньше закрывался в тот миг, когда длина пересекала цель. Это отбирало у игрока
остаток поля: собрал нужное — дверь захлопнулась, хотя на доске ещё есть кого съесть.

Теперь **партия идёт, пока змея может расти**, а нижняя отметка — порог: взял — в
подвале видно, сколько отметок уже твои и сколько до следующей, и появляется кнопка
«Забрать». Кнопка есть только тогда, когда остановиться уже законно, поэтому это не
лишний тап, а решение: добирать ли остаток ради звезды, рискуя завалиться.

**Конец считается, а не угадывается.** `canGrow()` отвечает точно, а не «есть ли обед»:
выпуск сам по себе не растит, но убирает змею с поля и может открыть перекрытый луч.
Число змей строго убывает с каждым ходом, значит граф ациклический и обход конечен.
Бюджет узлов — предохранитель: не доказали за отведённое, отвечаем «может расти», потому
что закончить партию раньше времени хуже, чем дать лишний ход по мёртвому полю.

`node ending.mjs hvostoed.jsx` сверяет `canGrow` из игры с честным полным перебором на
каждом состоянии вдоль всей партии: 264 состояния, расхождений ноль. Стоит в CI.

**Где это реально меняет игру.** Замер по существующим уровням: цель почти везде и есть
потолок (перебить можно лишь на 4 из 33, на 2–3 клетки) — рукодельные уровни давно
подогнаны впритык. А вот у сгенерированных запас настоящий: +2…+12, потому что обманки
и есть запас. То есть свобода «доиграть» работает ровно там, где играют — в мастерской.

**Чем это кончилось.** Третья звезда «съедено всё поле» так и осталась недостижимой —
и автопобеда была ни при чём: эти доски просто нельзя свести к одной змее обедами, а
колючую нельзя съесть в принципе. В v6 звёзды переехали на шкалу длины (§5), и правило
конца партии наконец работает на то, ради чего писалось: каждый лишний обед двигает к
следующей отметке. Порог теперь — нижняя отметка, а не цель.

## 3b. Мосты, спящие и колючие (v4)

Три модификатора поля, отобранные по одному правилу: механика имеет право на жизнь,
только если взаимодействует с ядром — наследованием прицела, сдвигом хвоста, прямой
линией обзора или бюджетом массы. Управление при этом не меняется никогда: один тап.

**Мост** — клетка пола, над которой луч проходит всегда, что бы на ней ни лежало.
Тело едока ложится поверх чужого; пересечься змеи могут ТОЛЬКО на мосту, и занятость
там никогда не читается — ровно потому, что луч через мост не останавливается. Это и
делает механику дешёвой: единственная неоднозначность модели живёт там, куда модель не
заглядывает. Побочное правило: змею, чей хвост лежит на мосту, с этого направления не
съесть.

В генераторе мост ценнее, чем в игре. Обратное построение держит клетки зазоров
пустыми — иначе луч не долетит. Мост снимает этот запрет ровно на одной клетке, и
значит на ней МОЖНО кого-то поселить. Отсюда правило: мост без змеи на нём
бессмыслен, это просто пол, — поэтому обманка сажается прямо на мост. Замер: **все
мосты во всех пресетах пересекаются решением, и под каждым лежит змея** (4/4, 4/4,
8/8, 8/8 по четырём пресетам).

**Спящая** съедобна, но сама не ходит. **Колючая** наоборот — ходит, но её хвост не
съесть. Совмещать не даём — колючая соня была бы валуном в форме змеи. Обманке
достаётся любая из двух; в решении спящей может быть кусок, который в плане ни разу
не ест (см. «Спящая — в решении»), а колючей — только та змея, что ест ПОСЛЕДНЕЙ
(см. «Колючая, которая ест последней»): любой другой кусок по построению кем-то
съеден, и шипы на нём порвали бы план.

Приёмка потребовала одной правки, и она поучительна. Критерий `decoyLive` (обманку
либо можно съесть, либо она может пойти) стал валить мостовые обманки: они часто не
могут ни того, ни другого. Но их работа — стоять поперёк луча и врать, что путь
закрыт; они соблазняют самим фактом. Поэтому мостовые исключены из `decoyLive`
явно, а то, что решение через них проходит, гарантировано построением и перемерено.

Каждая механика заведена ОДНОВРЕМЕННО в трёх местах — игра, генератор, солвер, —
иначе замеры лгут. Доска (`boardOf`) собирается из уровня в одном месте, чтобы игра,
планировщик и мастерская читали одно и то же.

**Спина поворота — стена, и на неё это правило распространяется целиком.** Занятость
клетки читалась РАНЬШЕ плитки, поэтому змея, легшая на поворот, отменяла его вовсе:
луч, упиравшийся плитке в спину, спокойно съедал лежащий на ней хвост — обед сквозь
стену. Прислано игроком, воспроизведено по коду партии. Теперь закрытая сторона
проверяется до занятости, во всех трёх копиях механики (игра, генератор, солвер).

За это пришлось заплатить отрисовкой, и плата обязательная: перекрытая плитка не
видна, а невидимая стена — это авария, которую нельзя предвидеть. Поворот теперь
рисуется двумя слоями, как мост: жёлоб под змеями, стенки закрытых сторон ПОВЕРХ.

Планировщик о правиле знает: клетка, где луч решения останавливается (хвост жертвы),
и клетка с плиткой больше не совмещаются — в обе стороны. Проверка вперёд осталась
на нуле, повороты доезжают в 98–100% сборок.

**Вторая половина того же правила: стенка держит луч и ИЗНУТРИ.** На следующий день
пришла жалоба слово в слово той же: «змея прошла через стену, чтобы съесть чужой
хвост». Код партии воспроизвёл её ровно — и показал, что доска собрана движком ДО
правки выше (ход, которым игрок доел до цели, сегодня даёт `turnBack`), то есть
человек играл на странице, застрявшей в кэше service worker'а. Соблазн был закрыть
вопрос этим. Но проверка настоящим `raycast` на месте нашла рядом ЖИВУЮ дыру, которую
первая правка не закрыла.

`raycast` начинает цикл с ШАГА, поэтому клетку самой головы он не читает никогда. А
голова вполне может лежать на плитке поворота: после обеда едок встаёт на клетки жертвы
и перенимает её направление. Тогда луч рождается ВНУТРИ жёлоба — и стенку собственной
плитки не проверял никто. Змея в жёлобе стреляла в закрытую сторону и съедала хвост за
стеной, то есть та же авария, только зеркальная.

Замер до правки: на 278 собранных досках голова оказывалась на плитке 10 раз, и 4 из
них смотрели в стенку. Примерно каждая семидесятая доска уезжала к игроку со змеёй,
умеющей стрелять сквозь стену, — и проверка вперёд её пропускала, потому что сама
считала так же.

Выбора между «гнуть» и «остановить» тут нет, и это важно: изгиб выбирает выход по
стороне ВХОДА, а у луча, родившегося внутри плитки, стороны входа не существует. Значит
открытая сторона выпускает, закрытая останавливает. Правило поворота стало симметричным
и коротким: **стенки держат с обеих сторон, изгиб работает только на пустой клетке.**

Крестик аварии сдвинут на саму стенку (46 px от центра — там же её рисует `TurnWalls`):
в центре клетки лежит голова, и крестик поверх неё читается как «змея сломалась», а не
«здесь глухо».

Проверяется это теперь регрессией, а не статистикой — оба раза правило ломал не редкий
уровень, а порядок чтения клетки. `plancheck.mjs` держит доску, собранную руками под обе
жалобы, и гоняет по ней все три копии механики: игра, генератор, солвер × три случая
(изнутри в стенку, изнутри в открытую, снаружи в спину при лежащем на плитке хвосте).
На коде до правки падают ровно три ответа из девяти — по одному на копию.

Цена измерена, и она в пределах шума: выработка приёмки на 150 сидах × 5 пресетов
19.1% → 18.7% (143 доски из 750 против 140). Три доски из семисот пятидесяти теперь
бракует проверка вперёд — ровно те, чей план опирался на выстрел сквозь стенку.
Змей, стреляющих сквозь стену, среди принятых досок было 2 из 143, стало 0 из 140.

**Поворот** — плитка пола, соединяющая две стороны клетки из четырёх. Луч, вошедший с
открытой стороны, выходит в другую открытую; вошедший с закрытой — авария, как о валун.
У плитки есть спина, и она заодно бесплатно работает препятствием. Занятость клетки
перекрывает ИЗГИБ, но не стенки: изгиб выбирает выход по стороне входа, а у луча,
остановленного чужим телом, выхода уже не будет. Стенки же держат независимо ни от
чего — см. две записи ниже, обе оплачены жалобами игроков.

Сомнение было в читаемости — в Arrows путь нарисован, а у нас луч невидим. Довод
оказался слабым: пол сложен из квадратов, трассировка идёт клетка за клеткой без
двусмысленности, и поворот на плитке не сложнее прямого луча, просто длиннее.

**В коде поворот дешевле, чем кажется.** Путь обеда уже хранился списком клеток, а не
отрезком (`pathCells = ray.gap.concat(prey.cells.reverse())`), поэтому рост, поедание,
сдвиг хвоста и анимация не потребовали НИ ОДНОЙ правки: изогнутый луч — это просто
список, который поворачивает. Прицел после обеда встаёт сам, он считается как «голова
минус шея». Прямую линию предполагали ровно два места — рисование луча (стало ломаной)
и путь выпуска.

**А вот в генераторе поворот меняет главное.** `splitOptions` целиком стоял на
коллинеарности: весь участок разреза обязан лежать на прямой. С поворотами прямизна
нужна только НА ВХОДЕ — прицел едока смотрит в первую клетку зазора, — а каждый изгиб
внутри становится плиткой. Это снимает структурный потолок бюджета пустот, который
брался ровно из нужды в длинных прямых. Замер на «пустотах» (цель 30): без поворотов
доступно ~16, при трёх ~22, при шести ~25, дальше упор примерно в 0.85 цели. Бюджеты
пресетов подняты соответственно (пустоты 16 → 22, простор 26 → 33), и теперь он
выбирается ТОЧНО, а не с недобором.

Плата: плитка остаётся на полу навсегда и гнёт все лучи через клетку. Поэтому вместе с
вариантом разреза возвращается список нужных плиток и список клеток, проходимых
насквозь; на каждой клетке возможен либо поворот, либо сквозной проход, и две разные
плитки на одной клетке несовместимы. Совместимость проверяется со всеми уже принятыми
ходами, проверка вперёд — последний рубеж.

Замер: **все повороты во всех пресетах пройдены решением** (9/9, 10/10, 13/13, 13/13) —
декоративных нет. Тапов в спину поворота на старте 0–1 из 55–110, то есть закрытая
сторона опасна, но поле не превращается в минное.

**Чего сознательно нет.** Правила размера («нельзя есть длиннее себя») — оно режет
примерно половину вариантов разреза на каждом шаге. Таймеров и движущихся объектов —
они ломают обещание играть без давления.

## 3c. Яблоки и порталы (v5)

**Яблоко** — не механика, а следствие правил. Съесть можно только за хвост; у змеи
в одну клетку хвост и есть она сама, и едок вырастает ровно на её длину — на единицу.
Луч, зазор, проверка вперёд, подсказка, солвер и код обмена работают с яблоком как с
любой другой добычей, потому что это она и есть. Единственное ограничение тоже выведено,
а не назначено: у одной клетки нет направления взгляда, значит ходить яблоко не может
никогда, — оно всегда спящее.

Генератор строит яблоки обратным ходом, разрешая добычу длиной 1. Место им там же,
где передышки: ход на яблоко безрисковый. Выгода структурная: обычный ход тратит целый
кусок змеи, а яблочный — одну клетку, поэтому предел числа ходов поднимается с
(цель−2)/2 до (цель−2+яблок)/2, и куски к концу обратной прогулки остаются длиннее.

**Портал** направлен: вход и выход. Луч, дошедший до входа, продолжается от выхода тем
же направлением. Занятость клетки проверяется раньше портала — лёгшая на вход змея его
перекрывает, ровно как у поворота. Клетка выхода читается как обычная: лежит на ней
кто-то — луч в него и врежется. Тело едет за лучом и ложится на доску двумя кусками.

Вся геометрия скольжения стоит на том, что соседние клетки ровно на CS друг от друга:
путь размечен по индексу, а не по длине. Портал ломает ровно это, поэтому такой отрезок
не интерполируется, а перескакивается — по времени тот же шаг, по месту мгновенный.

Генератор кладёт финальную змею отрезками: отрезок кончается в клетке X, следующий
начинается в клетке E где-то ещё и обязан сделать первый шаг в ту же сторону, каким
кончился предыдущий. Луч идёт по убыванию индексов, поэтому портал E→X при таком
условии сохраняет направление сам собой. Отрезок не короче трёх клеток: у куска должны
быть голова и шея по одну сторону разрыва, иначе у змеи нет взгляда.

### Портал не спрашивает разрешения (найдено замером)

Проверка вперёд валила **каждый пятый** построенный уровень («пустоты» 20%, «простор»
24%) — уровень строился, но игра не проходила собственный план генератора. Ловила это
приёмка, до игрока брак не доезжал, но выход генератора резало вдвое. Причин оказалось
две, и обе — про одно и то же заблуждение: что портал работает только тогда, когда он
нужен плану.

**Портал в зазоре срабатывает ВСЕГДА.** Отменяет его ровно одно — занятость клетки, а
клетки зазора обязаны быть пусты. Перебор разрезов же считал порталом только тот, что
уносит луч ровно по плану, а остальные молча числил обычным прямым шагом. Игра ныряла в
портал, до жертвы не долетала. Вариантов ровно два: либо портал ведёт туда, куда идёт
разрез, либо разреза нет, — так теперь и написано.

**Мост отменяет всё, что было на клетке.** В `raycast` он стоит первым: раньше
занятости, раньше портала, раньше поворота. Значит мост — не «клетка, где не читается
занятость», а «клетка, где не читается ничего». Мост, севший на вход портала, молча
выключал перенос, на который рассчитывало решение; мост на хвосте жертвы означал, что
луч над обедом пролетит. Отсюда два новых запрета на клетку под мост: не клетка портала
(вход или выход) и не клетка, где луч решения ОСТАНАВЛИВАЕТСЯ.

После обеих правок проверка вперёд проваливается **0 раз из 2000** сборок по пяти
пресетам, а выход мастерской вырос в 2–3 раза (попыток на уровень: средний 9→5,
длинный 5.5→2.4, пустоты 12→6.7).

Заодно `verify()` собирал состояние своей сборкой, теряя `spiky` и `sleep`, — то есть
проверял доску, где колючий хвост съедобен, а собственная проверка «спящую заставили
ходить» не могла сработать никогда. Теперь через `stateOf()`, как все остальные.

Луч можно замкнуть в кольцо, поэтому во всех трёх раскастах стоит предел шагов и авария
«луч ушёл по кругу».

### Пометка обязана работать

Правило, оплаченное замерами: пометка на змее — не краска. И колючая, и спящая
отличаются от обычной ровно тогда, когда чей-то луч достаёт до их ХВОСТА: у колючей
это авария вместо обеда, у спящей — обед, который гарантированно не уползёт. Поэтому
генератор ищет клетки, куда луч долетает по ходу решения, и сажает помеченную хвостом
туда, а метрика `markUse` держит это в приёмке. Так же и рельеф: `terrainUse` требует,
чтобы каждый мост, поворот и портал лежали на луче решения хоть раз.

Три ошибки, каждая ценой половины пометок: ставить приманку ДО обычных обманок
(следующая встаёт перед ней), считать лучи по доске без обманок, и позволять телу
приманки лечь на подлёт к собственному хвосту. Портал вдобавок коварен: змея может
просто лежать сквозь него от начала до конца, и ни один ход его не тронет (так выходило
в 34% случаев).

**Спящая — в решении.** Хода «просто пойти» в игре нет: любой ход — обед или вылет.
Значит кусок, который в плане ни разу не выступает едоком, вперёд по времени не двигается
вообще, и «спит» — правда о нём, а не ограничение.

### Колючая, которая ест последней

Здесь раньше стояло: «колючую в решение поставить нельзя — непоедаемым может быть лишь
кусок, которого план не ест, а такой ровно один, змея-победитель; пометить её шипами
значило бы выдать игроку, какую растить». Первая половина фразы сама себя опровергает:
раз такой кусок есть, значит поставить можно. Вторая — вопрос вероятности, а не запрета.

Итак, колючей может быть **та змея, что ест последней**, и никакая другая: все
остальные куски по построению кем-то съедены, и шипы на них вернули бы лучу
`spikyTail` вместо `tail`, то есть порвали бы план на этом самом ходу. Хвоста
победительницы план не касается ни разу — шипы на ней плану ничем не грозят.

Зачем это нужно. Пометка на победительнице говорит игроку ровно то, на чём в кампании
держатся «Западня» и «Обжора»: **эту не убрать, её придётся кормить**. И это не
украшение задним числом — шипы закрывают тап, который без них был бы законным обедом,
то есть меняют само пространство решений. Раньше генератор такой уровень собрать не
мог, хотя рукой они собирались с самого начала.

Выдаёт ли это ответ? Выдавало бы, будь оно правилом. Поэтому монета: половина сборок
отдаёт шипы приманкам, половина — победительнице, и по доске эти два случая
неразличимы. Монету отменяет только нехватка обманок: если колючих заказано больше,
чем влезет в приманки, победительнице шипы нужны обязательно — иначе ручка останется
недобранной. В модалке потолок ручки поэтому стал `обманки + 1`.

Пометка и здесь обязана работать. Хвост победительницы по плану не ест никто — значит
смотреть в него должен кто-то посторонний. Генератор сначала ищет такого среди уже
стоящих (это бесплатно, но редко: 6 случаев из 46), а если такого нет —
сажает **наблюдателя**: обманку, чья ГОЛОВА смотрит змее в хвост. Тап по наблюдателю —
авария, ходом он быть не может, поэтому в `decoyLive` он не считается, как и приманка;
работает он или нет, меряет тот же `markUse`. Слот он занимает обманочный: пока в
бюджете есть место, вычитается из обычных обманок, а когда места нет — становится
лишним, ровно как приманка, которой не хватило слота.

Подлёт наблюдателя пускается только по клеткам, которых решение не касается НИКОГДА:
плитки поворотов и мосты лежат на клетках зазоров, порталы — на клетках финальной
змеи, то есть все они в запретном списке, и клетка вне списка — чистый пол навсегда.
А вот клетка ХВОСТА — чужая, решение на ней лежит, и пол под ней бывает любым: мост,
над которым луч пролетит, или спина поворота, о которую он разобьётся. Поэтому
последнее слово оставлено настоящему `raycast` на месте: без этой проверки каждая
сороковая победительница выходила с краской вместо шипов.

Замер (150 сидов на пресет, до → после): выработка приёмки 114 → 112 принятых уровней
из 600 попыток, то есть не изменилась; колючая ест последней в 46 из 112 принятых
(41%); брака по `markUse` стало МЕНЬШЕ — на «просторе» 39 → 33 из 120 собранных, на
«среднем» 17 → 12. Причина простая: приманка попадает в чужой луч не всегда, а
победительница со своим наблюдателем — почти всегда.

Независимый аудит (`node audit.mjs средний 8`, наборы уровней до и после разные, так
что это направление, а не точность): соблазн 17% → 20%, живых обманок 88% → 81%,
мёртвых змей 0.5 → 0.8. Ровно та цена, которую шипы и наблюдатель обязаны стоить: тап,
бывший обедом, стал аварией, а наблюдатель по определению никуда не ходит.

Ворота в CI: в `plancheck.mjs` заведён отдельный случай «колючая ест последней», где
колючих заказано больше, чем обманок, — значит шипы надеваются победительнице
обязательно, и каждый собранный там уровень игра обязана пройти своим ходом.

### Сколько механик на уровень

Ручка «сколько чего» не решает вопрос читаемости: ничто не мешает навалить мосты,
повороты, яблоки, колючих, спящих и порталы на одну доску разом — шесть правил поверх
базового. Для этого есть `mechs` — потолок РАЗНООБРАЗИЯ.

Он живёт в модалке, а не в генераторе, и это исправленная ошибка, а не деталь. Сначала
потолок стоял внутри `generate()`: лишние виды обнулялись случайным выбором по сиду,
«зато два уровня с одним конфигом окажутся про разное». Замер по пяти пресетам показал
цену: при `mechs: 2` из шести поднятых ручек портал доезжал до доски в 25% сборок,
яблоко — в 35%. Игрок поднимает «Порталов 2», собирает уровень — порталов нет, и
объяснить это нечем. Ползунок, который врёт о собственном значении, хуже отсутствующего.

Теперь правило одно и держится сверху донизу: **что стоит в конфиге, то и будет на
доске**. Потолок разбирается в модалке, на виду и обратимо в обе стороны — поднял
лишнюю механику, потолок подрос сам; опустил потолок, лишние механики обнулились
прямо на глазах, снизу списка. Генератор же строит ровно заказанное, а `shortfall()`
в приёмке отбраковывает уровень, где ручка заказала больше, чем доска отдала, и
разбор отказов называет, какую ручку отпустить.

Пресеты после этого называют свои настоящие числа: ученик 2, остальные 6.

## 4. Механики-модификаторы (v2)

**Валуны** (`rocks`) — статичные серые клетки: не съесть, не сдвинуть, блокируют луч. Формируют коридоры и щели.

**Колючие змеи** (`spiky: true`, оливковый цвет, шипы вдоль тела): их хвост **нельзя** съесть (тап чужой змеёй в колючий хвост = авария); сами они едят как обычные; выпустить их **можно**. Дизайн-манипуляция: колючую не убрать напрямую, но можно «покормить» — она съест кого-то, сдвинется и развернётся, открыв путь; либо её выпускают в правильный момент. Целевой паттерн (одобрен автором): колючка-«пробка» — её хвост закрывает вход в валунную камеру, кормление сдвигает пробку, но вытащить её из камеры сложно.

## 5. Звёзды — три отметки длины (v6, замер августа 2026)

**Было:** 1 звезда за победу, +1 если никто не улетел, +1 если на доске осталась одна
змея. Автор сказал про третью: непонятно, за что дают и как добиться. Полный перебор
достижимых состояний (код самой игры, как в `ending.mjs`) показал, что беда глубже.

| | ★2 «никто не улетел» | ★3 «осталась одна змея» | три звезды сразу |
|---|---|---|---|
| Кампания (25) | недостижима на **6** | недостижима на **9** | возможны на **8** |
| Пустота (19) | недостижима на **5** | недостижима на **3** | возможны на **10** |
| Генератор (15 принятых) | достижима везде | недостижима на **9** | возможны на **6** |

Вылет обязателен по построению на 11 ручных уровнях («Жертва», «Впритык», «Размен»,
«Западня», «Глубокая пробка», «Гордость», «Затор», «Балласт», «Пошлина», «Отступные»,
«Долгий счёт») — там вторая звезда невозможна в принципе; сверено независимым
`solver.js` (`sols=0` без выпусков), цифры совпали до числа. Колючую нельзя съесть
никогда, поэтому одна колючая обманка делает третью звезду недостижимой сама по себе.

### Почему звезда за состояние доски вообще не работает

Две структурные находки, ради которых стоило мерить, а не рассуждать.

**1. Ход всегда убирает с доски ровно одну змею** — обед жертву, вылет себя. Проверено
на всех достижимых состояниях 44 ручных уровней: нарушений 0. Следствие: число ходов
в партии = сколько змей ты убрал, то есть «за минимум ходов» — это «оставь на доске
побольше змей», ровно наоборот к «съедено всё». Отдельной оси «эффективность» в этой
игре нет, и звезду за неё ставить не за что.

**2. На 35 ручных уровнях из 44 ВСЕ победные концовки одинаковы** — по числу оставшихся
змей, по длине и по потерянной массе. Значит любая звезда, считанная по итоговой доске,
меряет уровень, а не игрока: она либо выдаётся всегда, либо не выдаётся никогда. Так и
жила вторая звезда: невозможна на 11 уровнях, даётся даром вместе с победой на 25,
и реально зарабатывается лишь на 8.

### Стало: шкала длины

Звёзды — три отметки **длины, до которой доросла змея к концу партии**. У уровня
объявлен `ceiling` — потолок поля, длина, больше которой доска дорасти не даёт, —
и отметки стоят на **0.5 · 0.75 · 1.0** от него (`marksOf` в `generator.mjs`, одна
формула на игру, генератор, метрики и ворота). Нижняя отметка она же порог победы.

Почему это чинит болезнь: потолок **считается**, а не предполагается. Прежняя третья
звезда предполагала, что потолок — это «одна змея», и колючая обманка ломала догадку.
Посчитанный потолок ломать нечем: на «Валунах» он равен 9 при 11 клетках на поле, и
две улетевшие клетки никому не мешают.

**Верхняя отметка достижима по построению.** У ручных уровней `ceiling` измерен полным
перебором концов партии и сверяется воротами: `solver.js` заново считает максимум
достижимой длины и падает, если объявленное расходится с доской (ни ниже — звезда была
бы даром, ни выше — была бы недостижима). У сгенерированных потолок равен длине
задуманного плана, а план проходит код самой игры (`walkSids` в `acceptCrafted`).

**Где ставить отметки — тоже замер, а не круглые числа.** Обед глотает змею ЦЕЛИКОМ,
поэтому длина растёт большими скачками, и отметка близко к потолку почти никогда не
оказывается ИСХОДОМ партии. Доли исходов случайной игры (400 партий на уровень, все
44 ручных):

| отметки | 0★ | 1★ | 2★ | 3★ | уровней, где 2★ выпадает ≥10% |
|---|---|---|---|---|---|
| 0.65 / 0.85 | 54% | 20% | **5%** | 20% | 7 из 44 |
| 0.6 / 0.8 | 45% | 23% | 12% | 20% | 17 из 44 |
| **0.5 / 0.75** | 35% | 28% | **17%** | 20% | **24 из 44** |
| 0.5 / 0.7 | 32% | 24% | 24% | 20% | 31 из 44, но 1★ проседает до 24 из 44 |

Взято 0.5/0.75: обе средние ступени населены. Ровно эти доли уже стояли на полях
рекорда — теперь вся игра меряется одной линейкой, и шкала в шапке у обоих режимов
одна и та же.

**Нижняя отметка обязана быть выше стартовой длины**, иначе звезда горит до первого
тапа: `marksOf` поднимает её до `старт + 1`. На двух уровнях места нет — «Затор»
(старт 5, потолок 6) и «Уведи хвост» (старт 6, потолок 8): весь рост уровня меньше
трёх клеток. Это свойство доски, а не ошибка, и ворота ругаются только когда место
БЫЛО (`потолок − старт ≥ 3`).

**Что уровни при этом не потеряли.** Доски не тронуты ни на клетку. У 39 уровней из 44
`target` просто переименован в `ceiling` (число то же), у пяти потолок оказался ВЫШЕ
прежней цели — перебор нашёл линию длиннее: «Очередь» 10→12, «Сапёр» 12→14, «Мельница»
9→10, «Тесный угол» 8→10, «Цепочка» (пустоты) 9→12. Там верхняя звезда теперь честно
выше того, что уровень требовал раньше.

**Что стало проще.** Порог победы опустился до половины потолка, поэтому уровень
провалить труднее: партия проиграна, только если массы на поле меньше нижней отметки.
Взамен появилось то, чего не было: «доиграть до конца» стало осмысленным действием, а
не капризом — каждый лишний обед двигает к следующей звезде. Правило конца партии
(§3a), написанное когда-то ради недостижимой третьей звезды, наконец работает на то,
ради чего задумывалось.

**Подсказка целится в потолок**, а не в нижнюю отметку: совет, обрывающийся на первой
звезде, бросает игрока там, где игра начинается. `hints.mjs` проверяет это на обоих
паках (раньше — только на «Пустоте»): 44 уровня, план доводит до потолка, самый
долгий счёт — 2 мс.

### Что гарантирует генератор

Верхняя отметка достижима по построению. Приёмка добавляет два коридора (`presets.mjs`):

* `starLow` — нижняя отметка выше стартовой длины (на 80 замеренных уровнях выполнено
  всегда, коридор стоит как страховка от вырождения);
* `starTop` — доля случайных партий, берущих ВЕРХНЮЮ отметку, не больше порога:
  ученик 0.9, средний 0.75, длинный и пустоты 0.5. Пороги поставлены по медиане на

## 6a. Пак 2 «Пустота» (19 уровней, отдельная линия)

Второй набор уровней, живущий рядом с кампанией и переключаемый вкладкой в меню. Заказ автора: **никаких валунов и колючек** — только базовые правила, простые и интересные уровни, у которых по возможности несколько путей решения; главная ставка — на «пустоту», то есть на **зазор**.

Почему зазор: пока голова идёт по пустым клеткам, хвост подтягивается ровно столько раз, сколько было пустых клеток. Значит **длина зазора = насколько змея переезжает по полю**. Из этого следуют два разных эффекта, на которых и стоит пак (клетки тела нумеруются от головы i=0 до хвоста L−1, зазор g):

- **g = L−1−i** — клетка i становится новым **хвостом**: бывшая стена превращается в еду (уровень «Переезд»);
- **g > L−1−i** — клетка i **освобождается**: строка или столбец открываются для чужого луча (уровень «Тесный угол»).

Первая версия бюджетных уровней (10×12–10×14, 13–14 змей, 12–13 ходов, слож≈24.5–25.8) оказалась неподъёмной даже для автора и **снята в levels-reserve.jsx**. Отсюда два правила для класса «бюджет»: пробка должна читаться (её хвост никто не ест, а голова уже смотрит в край, так что тап по ней — очевидный выпуск) и в шапке показывается **запас** — сколько длины ещё можно потерять (`hasBudget`/`slack` в Game; строка появляется только там, где цель меньше суммы клеток).

**Генератор бюджетных уровней** (`scratchpad/genbudget.mjs`) — новый класс, которого в проекте не было. Сначала строится обычный eat-all базис (мегазмея + обратные разрезы), затем считаются **клетки пустоты, через которые проходит цепь решения**, и в них сажаются 2–3 змеи-«пробки»: тело из свободных клеток, голова обязательно смотрит в край, чтобы пробку можно было выпустить. Цель уровня остаётся равной сумме базовых змей, поэтому масса пробок — чистый излишек, который придётся потерять. Отбор: уровень решаем; с нулём выпусков **не** решается; с одним выпуском тоже не решается (иначе жертва не «часть змей», а одна); ≥ 9 ходов; несколько решений; p(случайных ходов) в [0.02, 0.4]. Минимальное число выпусков считается отдельно — перебором с ограничением `maxLaunch`, и именно оно попадает в текст урока.

Координаты — в массиве `RAW_LEVELS_VOID` внутри hvostoed.jsx, формат тот же. Оба пака собираются функцией `buildPack` в массив `PACKS`; в меню — вкладки, звёзды хранятся по ключу `pack.id + ":" + номер`. Цвета раздаёт `paintPack`: по кругу из `ORDER`, но соседним змеям (клетки бок о бок) один цвет не достаётся — на полях с 10–11 змеями две однотонные змеи впритык читались как одна.

Координаты — в массиве `RAW_LEVELS` внутри hvostoed.jsx. Формат уровня: `{ name, lesson, w, h, target, moves?, rocks?: [[x,y]...], snakes: [{ cells: [[x,y]...], spiky? }] }`, голова каждой змеи — первая клетка, направление выводится из первых двух.

## 6aa. Пак «Азбука» (30 уровней, v7 — первый в меню)

Обучающая линия для игрока с нуля. Заказ автора: никаких механик и никаких
обманок — **каждая змея на доске входит в решение**, финал всегда одна змея
(`decoys: 0`, ходов ровно змей−1). Проиграть можно двумя способами: неправильный
порядок обедов запирает доску (никто ни на чей хвост не смотрит, рост невозможен)
или вылет теряет массу. Сложность регулируют только пустоты и порядок.

Собран `genintro.mjs` тем же конвейером `craftOnce`: шесть полос по пять уровней,
5×4/6 клеток → 10×12/30 клеток. Ключевая метрика отбора — **доля безопасных
обедов** (`eatSafety`): по всем достижимым состояниям — какая часть обедов
оставляет потолок достижимым. `safety` из levelstats для этого не годится: она
мешает обеды с вылетами, а вылет — не порядок, а потеря массы; уроки же пака
опираются на число буквально. Коридоры полос: A — eatSafety = 1.0 И starTop = 1
(урок «любой порядок доводит до конца» обязан быть правдой, тупая игра берёт
потолок); B — eatSafety < 1 (первый запирающий порядок обещан уроком); дальше
потолки 0.9/0.8/0.7/0.6 при starTop ≤ 0.7/0.4/0.25/0.15. Потолок каждого
кандидата сверен полным перебором (`ceilingOf` из solver.js) ещё при отборе:
потолок выше построенного — брак, а не поправка объявления.

Балл сложности уровня = (1−eatSafety) + 0.7·(1−starTop) + 0.3·min(avgGap/2, 1);
порядок в паке — по нему. Замер принятых: A 0.00–0.08, B 0.48–0.71, C 0.50–1.06,
D 0.77–1.46, E 1.04–1.38, F 1.25–1.47 — кривая монотонна по полосам. Пулы всех
полос набрали по 40 кандидатов из ≤500 сидов.

## 6ab. Режим «Комнаты» (прототип, v7)

Ответ на разбор Gamigion про Block Out: казуальность делает не концепт, а ширина
выбора в один момент времени. Плоская доска в «Хвостоеде» связывает размер с
глубиной планирования (замер «Азбуки»: на 10×12 eatSafety падает к 0.5). Комнаты
рубят эту связь: доска большая, но открыт квадрат; собери всех змей открытой
области в ОДНУ — откроется следующая комната со своими змеями, и та же змея
растёт дальше. Масса сохраняется — чемпион комнаты физически становится сырьём
следующей.

Правила режима: закрытая комната для луча — стена (авария, не вылет); вылетов
нет вовсе — любой неверный тап (тело, крышка, взгляд за край) доску НЕ меняет и
крутит счётчик ошибок; открытие комнаты — чекпоинт (истории назад нет, «Комнату
заново» возвращает к нему); звёзд нет — финал говорит длину и число ошибок,
onWin(3) лишь помечает уровень пройденным. Железное правило конструкции: из
КАЖДОЙ полной сборки комнаты остальные комнаты решаемы. В прототипе оно
обеспечено сильнее — финальная змея каждой комнаты единственна при любом
порядке (проверено перебором на стенде genrooms.mjs); ловушки порядка внутри
комнат остаются (запертых состояний 0·1·2·2 по комнатам).

Заодно пойман давний баг анимации: rAF передаёт время НАЧАЛА кадра, оно бывает
раньше performance.now(), снятого при старте, — отрицательный прогресс давал
индекс −1 и NaN ронял кадр. Ловился в «Комнатах» из-за частых тапов, но жил во
всех режимах. Зажат Math.max(0, …).

### Пак «Комнаты»: 30 уровней (v7)

Собран `genrooms30.mjs`. Шесть полос по пять уровней: 2 комнаты 5×5 (доска
5×10) → 4 комнаты (10×10) → 6 комнат (10×15). Полоса A целиком безопасна,
дальше в уровнях обязаны быть запирающие порядки (trapsMin по полосам
0·1·1·2·2·2), первая комната всякого уровня безопасна всегда. Порядок внутри
полосы — замеренный балл Σ(1−безопасность обедов) + 0.35·ловушек; кривая
0.00 → 2.30.

Два урока постройки. Первый: случайная посыпка змей по комнате не
складывается в цепочку (12 тысяч отказов startOk на 20 сидов) — стадия
строится направленно, как руками: новая змея садится либо хвостом под текущий
луч большой, либо головой на чистую линию к её хвосту, обед сразу применяется
к макету; если чемпион не дотягивается, в комнате растёт своя цепочка и
сшивается с большой, когда лучи сходятся. Решаемость каждой стадии — по
построению, перебор лишь подтверждает и меряет ловушки. Второй: у boardOf
генератора НЕТ валунов — прототипный стенд молча гонял лучи сквозь закрытые
комнаты (для единственности финала безопасно: надмножество ходов; для startOk
— нет). В genrooms30 крышка — честная стена: колючая спящая змея из всех
закрытых клеток.

Ворота: `roomscheck.mjs` (добавлен в pages.yml) пересобирает решение каждого
уровня перебором на механике генератора со стеной-заглушкой и проходит его
кодом самой игры с крышками-валунами, ход в ход. Сверх ворот: уровни 1, 15 и
30 пройдены в браузере по этим решениям, ошибок 0.

### Полоса G: пять плотных уровней обратным построением (v8)

Заказ автора: комнаты слишком пустые. Замер подтвердил — плотность новых змей
в комнате у полос A–F 16–48%, медиана 28% (ручные паки: «Азбука» медиана 35%,
«Пустота» 53%, поля «Рекорда» жили на 48–73%). Виноватой оказалась не приёмка,
а сам прямой строитель: на ручках пожирнее (perRoom 4–6, slen 2–4) полоса D
дала 0/40 при 25 тысячах отказов ПОСАДКИ — каждой новой змее нужна чистая
линия луча здесь-и-сейчас, и тесная комната захлёбывается; отказов
единственности финала при этом 6–7, то есть железное правило не мешало.

`genroomsdense.mjs` идёт от конца, как основной генератор: финал комнаты —
одна змея «новая масса ++ чемпион», и она режется обратными ходами. Разрез
впритык (зазор 0) не сдвигает ничей хвост, куски встают нос-в-хвост вдоль
пути — финал комнаты единственен ПО ПОСТРОЕНИЮ; разрез с зазором — «отрезать
кусок и сдвинуть хвост едока назад»: сдвиг чемпиона идёт по его же прежнему
телу и в данные уровня не попадает вовсе, сдвиг куска новой массы дорастает
хвост в свободные клетки.

**Ошибка первой сборки, оплаченная игрой автора.** Первая версия резала
почти всё впритык — и уровни прошлись жадным тапом по одной змее: разрезы
впритык вдоль одного пути КОММУТИРУЮТ, любой порядок склейки собирает тот же
финал, выбора нет (ровно об этом предупреждает шапка generator.mjs: без
доращивания доска — «одна нитка пути»). Хуже того: подмена в этой игре
бесшовна — съев чужого едока, перенимаешь его взгляд и доедаешь его жертву
сам, поэтому почти любой «неправильный» обед сходится к тому же финалу, и
случайные хвосты в чужих линиях жадного не ловят (замер: 2028 отказов жадной
пробы на 40 сидов). Отсюда три правила:

1. **Настоящий тупик — только замурованная линия.** Клетки при обеде не
   исчезают, поэтому хвост куска Q, дорощенный в зазор-линию, которую чемпион
   стреляет ПОЗЖЕ и законная жертва которой не Q, — честная ловушка: съешь
   висящего — его хвост ляжет на линию навсегда, жертва за ней осиротеет
   (сдвиг, который убирал хвост, уже не случится). Правильный ход — дать Q
   сначала съесть свою жертву и сдвигом уползти. Такую ловушку кладёт
   planTrap ДО раскроя: ищет в серпантине складку (клетки соседние на доске,
   далёкие по пути) и ставит границы кусков и зазор ровно туда; каждая
   комната со второй обязана нести одну.
2. **Жадная проба — в приёмке.** Симуляция «на каждом шаге ест самая длинная
   змея из имеющих обед» обязана ПРОВАЛИТЬСЯ в каждой комнате со второй —
   прямая метрика на жалобу «тыкаешь в одну змею, и она ест всех подряд».
   Плюс locked ≥ 1 и eatSafety ≤ 0.92 там же.
3. **Складкам нужно место.** В комнате 5×5 масса 12–14 клеток — два с
   половиной ряда серпантина, складки и прямые границы разрезов не
   пересекаются (0 планов на 500 путей); прижимной шаг к тому же складывал
   путь кольцом по периметру, а у кольца складок нет. Комната полосы — 6×6
   (доска 12×18), путь 18–22 клетки с приоритетом прямого шага 0.75.

Попутно пойман off-by-one в straightCut: проверялись шаги внутри зазора, но
не последний — от зазора к хвосту жертвы (`t > b` вместо `t >= b` из
splitOptions). Зазоры садились на изгибы, и НИ ОДНА стадия с зазором не
игралась вперёд (startOk 0 из 111 построенных) — та же категория ошибки, что
уже ловили в ending.mjs.

Выработка 35/40 сидов, отказы после починки: startOk 0, единственность 0 —
вся отбраковка ушла в геометрию посадки. Отобранные пять (уровни 31–35):
баллы 3.35 → 3.97 (полоса F: 1.25–1.47), ловушек 5 из 5 возможных в каждом,
безопасность обедов в комнатах-ловушках 0.46–0.71, плотность новых змей по
комнатам 47–58% против 16–48% (медиана 28%) у полос A–F, финальные змеи
108–117 клеток. Ворота те же: roomscheck проходит все 35 уровней кодом игры
ход в ход.

## 6b. Режим рекорда (пак «Рекорд» УДАЛЁН в v6, поля жили в `RAW_FIELDS`)

Заказ автора: таб «Рекорд» из игры убран целиком — вместе с тремя полями 12×16, их
данными и воротами `records.mjs`. Причина простая: со звёздами-отметками (§5) целевой
уровень и сам стал шкалой длины, и отдельный режим «на счёт» перестал быть отдельным.
Сам режим (`mode: "record"`) остался живым в мастерской — его собирает пресет
«простор», и рекорд по-прежнему живёт в localStorage (`hv-records`, ключ `pack:idx`).
Данные полей лежат в истории git; таблица ниже — что это было.

| поле | змей | клеток | плотность | потолок | чем доказан | случайная игра | ходов в лучшей линии | еды через пустоту |
|---|---|---|---|---|---|---|---|---|
| Большая пустошь | 29 | 140 | 73% | 140 | цепь «съесть всё» | медиана 36, p95 59 | 28 | 39% |
| Разлёт | 22 | 98 | 51% | 58 | лучшая линия beam | медиана 18, p95 39 | 13 | 69% |
| Порознь | 21 | 92 | 48% | 66 | лучшая линия beam | медиана 24, p95 35 | 13 | 77% |

**Как строится поле.** Гамильтонов путь по доске тасуется backbite-ходами, из него
берётся кусок, который режется на змей в местах, где путь идёт прямо. Тогда голова
каждого куска смотрит ровно в хвост предыдущего, и цепь «съесть всё» существует по
построению. Резать надо **с зазором**: при стыке впритык ничей хвост не сдвигается,
поэтому склейки не мешают друг другу, порядок не важен и поле проходится тупым
локальным правилом (проверено: «первый попавшийся» брал 128 из 128).

**Три вещи, которые стоили времени и которые нельзя забыть.**

1. **Нарезка одного пути делает съедобным всё сразу.** Каждый кусок по построению
   нацелен в предыдущий, поэтому на старте живы почти все связи (28 из 29 змей) и
   ветвление держится около 15 вне зависимости от плотности. Разрежение поля пустотой
   меняет длину лучей, но не число вариантов.
2. **Разрежать надо выбрасыванием кусков, а прицел — разворотом змей.** Удаление части
   кусков роняет плотность и ветвление, но само по себе не превращает стык впритык в
   дальний выстрел: ориентация змей остаётся прежней. Дистанцию даёт отжиг по
   разворотам отдельных змей.
3. **Нельзя гнать стыки впритык в ноль.** Линейный штраф за них выдавливает
   адъюцентность до нуля, и поле остаётся без единого очевидного хода — играть в такое
   утомительно. В целевой функции стоит `|adjN − 1|`: примерно один очевидный ход на
   ход как передышка между выстрелами.
4. **Нельзя оптимизировать долю дальних ходов.** Доля тривиально доводится до 100%
   превращением поля в неиграбельное: если ходов всего три и все дальние — доля
   идеальна. Оптимизировать надо число дальних ходов при живом поле, а в критерии
   держать живучесть = медиана случайной игры / потолок (рабочий коридор 0.25–0.6:
   ниже — единственная нитка решения, выше — поле само себя проходит).

Критерии приёмки поля: плотность 45–55%, дальних ходов 3–6 на ход при стыках впритык
≤1.5, живучесть 0.25–0.6, тупые стратегии ≤70% потолка, лучшая линия ≥10 ходов.

## 6c. Подсказка: один верный ход за раз

Лампочка в шапке. Каждое нажатие делает **один** ход настоящей лучшей линии — можно
натыкать её подряд и увидеть правильный порядок целиком. Ход проигрывается как обычный
тап: с анимацией и в историю, поэтому откат работает как всегда.

Линия ищется теми же `raycast`/`applyEat`, что и сама игра, — подсказка не может
разойтись с правилами. На целевых уровнях это **кратчайшая** победа (итеративное
углубление, общий бюджет 150k узлов на все глубины, чтобы безнадёжная позиция не
подвесила вкладку). На полях рекорда — **самая длинная** змея, какую находит перебор
в ширину (ширина 160: на всех трёх полях даёт то же, что и 320).

План кэшируется целиком картой «состояние поля → змея, по которой тапать»: пока игрок
идёт по линии, следующая подсказка бесплатна; сошёл — считаем заново. Первый расчёт:
150–200 мс на разрежённых полях, ~800 мс на «Большой пустоши» (29 змей) и на самых
больших целевых уровнях.

**Рекорд в партии с подсказками не засчитывается** — иначе кнопка обнуляет весь смысл
режима. Счётчик подсказок висит на самой кнопке, на экране конца партии — строка
«партия с подсказками, в рекорд не идёт». Проверка: `node hints.mjs hvostoed.jsx`
прогоняет вырезанный из игры код подсказки по всем уровням и полям и требует, чтобы
план доводил до цели (за минимальное число ходов) и до заявленного потолка.

## 6d. Генератор обратного построения (`generator.mjs`, `presets.mjs`, `audit.mjs`)

Уровни больше не ищутся перебором вслепую, а **строятся с конца**. Кладём одну змею
нужной длины — это финальное состояние — и раз за разом отменяем обед:

    M = B ++ реверс(зазор) ++ A_тело
        └жертва┘             └едок без проеденного хвоста┘

выбираем длину жертвы и длину зазора, освобождаем зазор и **возвращаем едоку хвост,
который он проел**, доращивая его в любую свободную сторону.

**Почему отмена обеда самодостаточна.** Forward-ход «A ест B» съедает и зазор, и
доращенный хвост, и доска возвращается ровно в M. Значит отмена не может сломать
более поздние ходы — достаточно проверить, что хвост лёг на свободные клетки. Обманки
так не работают: они остаются на поле навсегда, поэтому им нужен запретный список —
клетки, занятые кем-либо в любой момент решения, плюс все клетки зазоров.

**Что это дало.** Выход вырос с ~1% (перебор вслепую) до **99%**: 198 сидов из 200
дают уровень, проходящий проверку вперёд, расхождений ноль. Длина решения задаётся, а
не обнаруживается: солвер подтверждает задуманное число ходов в 13 случаях из 14
(четырнадцатый ловится критерием «нет решения короче»).

**Доращивание хвоста** отвязало доску от одной нитки пути: у едока появляется тело,
которого в исходной змее не было, поэтому после двух-трёх разрезов доска перестаёт
быть путём. Раньше это была главная беда — каждый кусок по построению целился в
предыдущий, отсюда ветвление около 15 и «съедобно всё сразу».

**Ветвление обратного обхода** (резать можно любую змею, а не всегда одну) превратило
решение из цепочки в дерево. Аудит: на «среднем» едоков 3.3, длиннейшая цепь одного
едока — 46% ходов; на «длинном» 4.7 и 37%. Ветви независимы, поэтому порядков много —
именно то, чего мы добивались с самого начала.

### Бюджет пустот, разгон и передышки

Раньше зазоры набирались вслепую (вероятностная тяга `gapPull`) и отбирались приёмкой,
то есть добывались отбраковкой. Теперь **бюджет задаётся**: `voids` — суммарная длина
пустот за всё решение.

Что эта величина значит на самом деле, выяснилось при замере:

* **Плотность она не меняет.** Обед сохраняет массу (едок прирастает ровно на жертву),
  поэтому занятых клеток всегда `цель + обманки`, при любых зазорах.
* **Зато она равна следу решения.** `след = цель + Σпустот` — тождество с точностью до
  клетки-двух (когда зазор совпал с клеткой, занятой в другой момент). То есть бюджет
  говорит, насколько решение больше собственной цели.

**Потолок структурный.** Разрез с зазором k требует змеи длиной ≥ k+3, а к концу
обратной прогулки куски короткие: суммарная длина сохраняется и делится на всё большее
число змей. Практический предел Σ ≈ 0.5·len; замер по пресетам (maxGap 5, прямизна
0.85): ученик 7, средний 10, длинный 16, пустоты 16, простор 28.

**Огибающая и фактура — разные вещи.** `peak` (0…1) задаёт, где сложность максимальна:
1 — разгон до финала, 0.6 — перевал в середине и лёгкий доужин, 0 — тяжёлый вход.
`breather` ставит ход вплотную каждый N-й **независимо от огибающей**: очевидный ход
нужен как выдох между трудными, а не как «лёгкий среди лёгких» в начале уровня. Финал
передышкой не бывает никогда.

Было у «простора» `[0,0,1,0,1,1,1,1,1,4,3,4,4]` — вся передышка потрачена авансом,
дальше четыре тяжёлых подряд. Стало `[0,0,1,1,0,2,3,0,3,4,0,5,5]`.

**Выбор реза идёт по нужному зазору среди ВСЕХ змей**, и лишь при равном k предпочитается
змея по `branch`. Иначе бюджет не выбирается: у взятой наугад змеи может просто не
оказаться длинной прямой под зазор — на «пустотах» это стоило трети бюджета.

**Наклон сложности приходится перемеривать.** Построение задаёт только зазоры, а
сложность — это ещё и число способов ошибиться, и оно вырастает из геометрии. Замер
показал, что это две разные кривые и структура тянет их в стороны: зазоры растут к
финалу (змеи длинные — прямые длинные), а число живых змей падает, то есть способов
ошибиться к концу меньше. `S.curve()` меряет обе по факту вдоль задуманного решения:
`tiltGap` против `tiltRisk`.

### Приёмка в два захода

Дешёвые метрики (форма поля, живость обманок) считаются первыми, дорогие (полный обход
достижимости, подсчёт решений) — только для переживших. Это ускорило пресет «пустоты`
с 17 секунд на уровень до 1.1.

Стоимость на маке: ученик 10 мс, средний 95 мс, длинный 0.8 с, пустоты 1.1 с,
простор 0.5 с.

### Аудит: чего приёмка не видит

`node audit.mjs <пресет> <сколько> <рисунков>` меряет то, чего **нет** в критериях, —
именно так и нашлась ошибка. Метрики: доля вынужденных ходов, мёртвые змеи, живые
обманки, соблазн (доля тапов в тупик), верные первые ходы, форма решения (едоков /
длиннейшая цепь), пустые четверти поля.

**Найденный изъян:** на двух уровнях из восьми две обманки из трёх не участвовали ни в
чём — декорация вместо соблазна. Приёмка этого не видела, потому что я о таком не
подумал. Добавлен критерий `decoyLive`: обманку либо можно съесть на старте, либо она
сама может пойти. После починки мёртвых змей 0.0, живых обманок 100%.

**Изъян в самом аудите** (та же болезнь, что когда-то у `verify()`): состояние он
собирал своей сборкой — без пометок и без доски, — то есть мерил поле, где колючий
хвост съедобен, спящая ходит, а мостов, поворотов и порталов нет вовсе. Пока все змеи
были длиной от двух клеток, это молча искажало числа; с приходом яблок (змея в одну
клетку) у сборки не стало направления взгляда, и аудит начал падать при запуске.
Теперь состояние идёт через `stateOf`, доска — через `boardOf`: одно место на всех.

### Обманка обязана ИГРАТЬ, а не лежать мебелью

Жалоба была простая: «обманки видно, что их трогать не надо, из них кашу не сваришь».
Замер подтвердил её целиком и объяснил, почему так вышло. Игра учит одному навыку —
проследить взгляд змеи; этот же навык и сортировал доску на дело и мусор.

Куда смотрит бодрая змея на старте (150 сидов, «средний» и «длинный»):

| | в чужой хвост (ход) | в стену | в край (вылет) |
|---|---|---|---|
| кусок решения | 90% | 8% | 0% |
| обманка | 18–23% | 34–39% | **42–48%** |

Тап по куску решения почти всегда ход, тап по обманке почти всегда авария или вылет.
Второй половиной беды была несъедобность: чей-то луч доставал до хвоста обманки у
7–15% из них, а за всю достижимую партию обманку не съедали и не давали ей съесть
никого в 43–68% случаев. Обманка была не соблазном, а мебелью — и мебелью, которую
видно.

**Почему ворота это пропустили.** Критерий `decoyLive` был сломан дважды. Числитель
считал ВСЕХ обманок (включая мостовых и приманок), а знаменатель — только обычных:
доля вылезала выше единицы (1.50 на «среднем»), и одна живая мостовая закрывала собой
двух мёртвых обычных. И вылет шёл в зачёт как «сама может пойти» — хотя это ход, при
котором змея пропадает с поля вместе со своей длиной, и добровольно его не делают.
Приёмка показывала 1.00–1.50, честный счёт давал 0.00–0.67: три уровня «среднего» из
пяти уехали с нулём живых обманок при коридоре `decoyLive: 1`.

**Починка постройки.** Машинки для правильной постановки в генераторе уже были — и
работали только на пометки. `trapSpots` ищет клетки, куда чужой луч долетает; `sightSpots`
— клетки, откуда виден чужой хвост. Обычную обманку теперь сажают ими же: голову в
клетку обзора (тап по ней — законный обед) или хвост под чужой луч (её саму можно
съесть), роли чередуются. Обещание проверяется настоящим `raycast` на месте: оба списка
считаются ОДИН раз, по доске без соседей, которых ещё не поставили, и обманка, легшая
раньше, запросто перекрывает подлёт к клетке следующей. Запасной вариант — бросок
наугад — тоже не молчит: из двух десятков бросков берётся первый, чей луч упирается в
чужой хвост.

`decoyLive` переписан честно (объединение «ею можно сходить» и «её можно съесть», по
тем же обманкам, что в знаменателе, вылет не в счёт), рядом встали `decoyMove` и
`decoyFood` — по слагаемому на каждую половину беды.

Что вышло (150 сидов на пресет, все обманки на доске):

| пресет | принято | тап=ход | вылет | съедена когда-нибудь | мертва |
|---|---|---|---|---|---|
| ученик | 30 → **35** | 37% → **73%** | 60% → **20%** | 28% → **54%** | 43% → **0%** |
| средний | 24 → **49** | 18% → **51%** | 48% → **23%** | 13% → **40%** | 68% → **19%** |
| длинный | 38 → **54** | 23% → **56%** | 42% → **16%** | 21% → **43%** | 55% → **17%** |
| пустоты | 21 → 13 | 18% → **46%** | 43% → **29%** | 20% → **45%** | 63% → **15%** |

Выработка выросла на трёх пресетах из четырёх при том, что ворота стали строже:
`decoyLive` перестал быть причиной отказов вообще. Остаточные 15–19% «мёртвых» — это
почти целиком колючие приманки, которых нельзя съесть по правилам, и мостовые.

Заодно похоронена гипотеза про форму: считалось, что обманки выдаёт изломанность
(они рисуются с `straightBias` 0.4, решение — с 0.7–0.85). На честном счёте (только
змеи от трёх клеток; двухклеточные считались «прямыми» и заваливали среднее решению)
излом решения 0.53–0.64 против 0.48–0.59 у обманок. Разницы нет, правка отменена.

### Ложная ветка: масса не наказывает, наказывает геометрия

Одиночная обманка видна насквозь через один тап: сходил, посмотрел, отменил.
Головоломка начинается там, где ложный путь держится несколько ходов. Держится он
бесплатно, потому что так устроен обед: голова едока проходит луч и доезжает до
ГОЛОВЫ съеденной, перенимая её направление. Значит цепочка взглядов — это цепочка
ходов: съел звено, смотришь туда же, куда смотрело оно, и следующий тап продолжает
ветку. Ручка «Ложная ветка (ходов)» стоит ровно столько обманок, сколько ходов
заказано.

**Первая сборка была неправильной, и ошибка поучительна.** Цепочка ставилась целиком
на клетках, которых решение не касается, и её головой была ещё одна обманка. Замер на
70 уровнях: в такую ветку не мог войти НИ ОДИН кусок решения, цель она убивала в 1–3
случаях из 20, а `safety` при этом РОСЛА (0.80 → 0.87), и число решений с 15 доходило
до 42. Ветка получилась не ловушкой, а ещё одним способом вырасти.

Объяснение стоит записать как правило: **при обеде масса поля не теряется, а сливается
в едока, поэтому лишняя масса в этой игре не наказывает НИКОГДА. Наказать может только
геометрия** — кусок решения, уехавший с того места, где он нужен плану.

Отсюда починка: хвост ПЕРВОГО звена садится под луч куска РЕШЕНИЯ, каким этот луч
виден со старта. Теперь ветку начинает не обманка, а участник плана, и, войдя, он
уезжает не туда. Каждое следующее звено садится хвостом на луч предыдущего. Собранная
цепочка проверяется ИГРОЙ прямо в генераторе: находим, кто может войти с доски как
она есть, и требуем, чтобы он прошёл ветку до конца (без этой проверки 15 собранных
цепочек из 33 не игрались вовсе — `tailSeen` отвечает про любой шаг плана, а тап
игрока случается на старте).

Приёмка требует, чтобы ветка НАКАЗЫВАЛА: `fakeTrap` проходит её целиком и спрашивает,
достижима ли ещё цель. Ветка, после которой цель жива, бракуется.

**Дверь — вот где всё стояло.** Первая сборка искала вход только на СТАРТОВОЙ доске, и
замер со счётчиками показал приговор: у 173 сборок из 200 дверей не было ни одной,
в среднем 0.3 на уровень. Тело звена и продолжение цепочки при этом почти не отказывали
(26 попыток → 25 готовых веток) — упиралось всё в единственное место. Причина —
свойство обратного построения: каждый кусок решения уже смотрит в свою будущую добычу,
а клетки, над которыми летят лучи плана, лежат в запретном списке, так что свободной
клетки на луче просто нет.

Дверь стали искать на КАЖДОМ шагу задуманного плана. Дверей стало 6.2 на уровень
(нулей 81 из 200 вместо 173), готовых веток — 107 из 200 вместо 25, и настоящих ловушек
среди них 49. Развилка, открывающаяся к третьему ходу, игроку не хуже стартовой, а
лучше: он идёт по решению, уже вложился — и тут видит поворот. Двери перебираются от
ранних к поздним (дверь на последнем шагу — развилка, до которой доходят уже
победителем); на счётчиках это не видно, но решает, КАКАЯ из возможных веток достанется.

Заодно выпрямилась и сама сборка цепочки: звенья теперь ставятся СИМУЛЯЦИЕЙ. Считать
«луч звена упирается в хвост следующего» по стартовой доске нельзя — съев звено, едок
накрывает телом и подлёт, и само звено, и луч с нового места идёт по другой доске,
запросто в собственный бок.

Итог на 150 сидах: при `fake: 2` принимается 16 уровней из 150 на «среднем» (было 6)
и 20 из 150 на «длинном» (было 6) против 49 и 54 без ветки. `safety` при этом держится
на 0.80 — и это честный ответ, а не разочарование: ловушка тут одна конкретная развилка,
а `safety` усредняет по всему пространству состояний. «Дорого ошибиться» здесь означает
не низкую среднюю безопасность, а гарантию, что в уровне ЕСТЬ ход на k тапов, после
которого цель мертва, и его проверили игрой.

### Мастерская в игре

Отдельная вкладка в меню: пресет → кнопка → уровень. Попытки крутятся пачками по шесть
с отдачей управления интерфейсу, иначе экран замирает. Сгенерированное принимается,
только если **его проходит код самой игры** — тот же планировщик, что стоит за
лампочкой: для целевого уровня план обязан существовать и не быть короче задуманного,
для поля рекорда потолком объявляется то, что игра реально сумела собрать. Уровни
живут в localStorage, у каждого есть «скопировать» — чтобы удачное можно было прислать
и вшить в игру насовсем.

## 7. Методология уровней — главный производственный актив

**solver.js** — запуск `node solver.js hvostoed.jsx` (можно сузить: `--pack=void`). Извлекает из файла игры **все** массивы вида `RAW_LEVELS*` (кампания и пак «Пустота») и проверяет каждый, проверяет геометрию (длины ≥ 2, связность тел, границы, пересечения, змеи не на валунах) и решает уровень полным перебором с мемоизацией. Метрики: решаемость, число решений (cap 500), минимум ходов, максимум длины без выпусков, «выпуск обязателен». **Железное правило проекта: ни один уровень не попадает в игру без прогона через солвер, причём проверяются данные, извлечённые из самого файла игры** — это ловит опечатки при переносе координат. Логика солвера (raycast/applyEat) обязана быть побайтово той же семантики, что в игре.

**ending.mjs** — запуск `node ending.mjs hvostoed.jsx`. Вырезает механику и `canGrow` из самого файла игры и сверяет их с независимым полным перебором на каждом состоянии вдоль жадной партии по всем пакам и полям. Ловит ровно одну вещь, но насмерть: партия обязана кончаться тогда и только тогда, когда рост невозможен. Стоит в CI перед сборкой.

**analyze.mjs** — запуск `node analyze.mjs <файл> [--json] [номер_уровня]`. Тот же извлекатель RAW_LEVELS (работает и с файлами-заглушками кандидатов, где есть маркеры `const RAW_LEVELS = [` и строка `];`). Сверх солвера считает: полное пространство состояний (каждый ход убирает ровно одну змею, поэтому граф — слоёный DAG), число тупиков, **p(случайных ходов)** — вероятность победы игрока, выбирающего случайный доступный ход (глубина стратегии), **p(случайных тапов)** — вероятность победы игрока, тапающего случайную змею при аварийной модели (опасность/читаемость поля), **мины** — среднюю долю заблокированных змей по достижимым состояниям, разметку первых ходов (какие ведут к победе) и эвристику сложности (калибровка: ~8.5 у «Разминки», ~14.4 у «Впритык»). Рисует ASCII-карту уровня. Это рабочий инструмент дизайнера: каждая правка уровня прогоняется через анализатор.

**gen2.js / gen3.mjs** — обратная генерация уровней класса «съешь всё» (gen3 добавляет посев валунов в клетки, не занятые прогулкой мегазмеи; уровни 22 «Крошки» и 25 «Обжора» получены им с ручной дочисткой). Строим финальную мегазмею случайной самонепересекающейся прогулкой по полю, затем режем её серией обратных разрезов. Разрез змеи M длины m: жертва P = M[0..k−1] (остаётся на месте), зазор = M[k..k+g−1] — обязан быть прямолинейным, едок E = M[k+g..m−1] плюс достроенный хвост из g клеток в свободных клетках; направление E должно смотреть вдоль линии на хвост P. Каждый разрез в точности обратим ходом «E съедает P», поэтому **уровень решаем по построению** — солвер потом лишь считает метрики и ложные ветки. Уровни 5 и 6 сделаны именно так. Генератор пока не знает про валуны и колючек — логичное расширение: сеять валуны до прогулки и помечать отдельные куски как spiky, затем фильтровать солвером.

Тюнинг сложности: target < total даёт «бюджет» на жертвы (ур. 3–4); ловушки — змеи со свободным выходом к краю, соблазняющие выпустить не ту массу; в аварийной модели добавились мины (заблокированные змеи, наказывающие невнимательный тап) и обеды, заводящие в тупик. Бывший приём «лимит ходов отсекает обходные решения» ушёл вместе с механикой лимита.

## 8. Анимация (реализована в v2)

Плавное скольжение по длине дуги через requestAnimationFrame — вместо покадровых прыжков по клеткам:

- Трек хода = развёрнутые клетки едока (от хвоста к голове) + путь (зазор + жертва от хвоста к голове). Все сегменты равны CS = 100 юнитов.
- Прогресс u ∈ [0..длина пути]. Голова на дуге h = (n0 − 1 + u)·CS; хвост подтягивается только на не-пищевой части пути (считается префикс не-пищевых клеток, уже пройденных головой). Точки полилинии сэмплируются между дугами хвоста и головы и пишутся в атрибут `d`.
- Жертва «всасывается»: её остаток рисуется от её головы до текущей точки головы едока; когда остаток < 26 юнитов, голова жертвы гаснет.
- Пульс головы при глотании: r = 43 + 9·|sin(π·frac)|; число длины в голове тикает по мере съеденных клеток — это «сочный» момент игры.
- Выпуск идёт с ускорением: u = pathLen·(0.3p + 0.7p²); clipPath обрезает змею за краем поля.
- Технически анимация императивная: DOM-ноды помечены `data-part` (outline / body / touch / stripes / spikes / headG / rotG / headCircle / num) и обновляются через ref + querySelector; React-состояние коммитится один раз финальным результатом (`finalSnakes` из `applyEat` — та же функция, что в солвере). Полоски хвоста и шипы скрываются на время движения и восстанавливаются вручную, потому что React их не диффит во время императивных апдейтов.
- `prefers-reduced-motion` → мгновенный коммит без анимации.
- Структура головы: headG (translate) → circle → rotG (rotate: глаза + язычок с CSS-мерцанием) → text — число не вращается вместе с глазами.

## 9. UX-инвентарь текущего прототипа

Tap-управление; авария при блоке: тряска + пунктирный луч + через ~0.7 с экран «Авария!» с объяснением (тело / голова / валун / шипы / уроборос) и кнопками «Продолжить» (бесплатно) / «Заново»; подтверждение выпуска («улетит с поля: −N длины»); всплывающее «+N» после еды; баннер тупика (показывается только пока выпуски ещё возможны); экраны поражения и победы со звёздами; undo и рестарт; меню с четырьмя правилами (вторая — «Смотри, куда она смотрит») и карточками уровней с заработанными звёздами. Прогресс живёт в памяти сессии: в артефактах Claude localStorage недоступен; при переносе в свой проект сохранение можно добавить первым делом.

а не как удовольствие. Урок: пульс головы и растущая цифра уже несут ритм

## 11. Названия

Русское рабочее — **«Хвостоед»**. Английский топ-кандидат — **Swallow the Leader**: каламбур на follow the leader, который буквально описывает механику наследования направления. Запасные: Tailbiter / Tailbite (прямой перевод), Tail Order (каламбур на tall order), Down the Hatch, Snakes & Snacks, Feast Mode. Осознанно избегаем шаблона «Snake …»: в сторах он занят .io-аренами, и пазл с таким именем утонет в выдаче.

## 12. Код: что где и как запустить

**hvostoed.jsx** — один файл, React-компонент с default export, иконки из lucide-react, стили инлайном плюс тег `<style>`; localStorage не используется. Внутренняя структура сверху вниз: `RAW_LEVELS` и `RAW_LEVELS_VOID` → `buildPack` → `PACKS`; чистая логика (`facing` / `occMap` / `raycast` / `applyEat`) — единая с солвером; `buildEatMove` / `buildLaunchMove` готовят данные хода для аниматора; геометрия скольжения (`ptAt` / `samplePts`); компоненты SnakeView / Rock / RayView; Game (состояние, rAF-аниматор, обработка ходов, победа/поражение); Menu; App.

Запуск как артефакт Claude: вставить файл в чат и попросить отрендерить. Локально: в корне проекта уже лежит `package.json` (Vite + react + lucide-react, `"type": "module"`); файл кладётся как `src/App.jsx`, запуск `npm i && npm run dev`; для теста с телефона — `npm run dev -- --host`. Проверка уровней: `node solver.js hvostoed.jsx` (нужен только Node; из-за `"type": "module"` солвер использует `import fs from 'fs'`). Расширенные метрики и ASCII-карты: `node analyze.mjs hvostoed.jsx` (тоже понимает `--pack=void` и номер уровня внутри пака). Проверка синтаксиса: `npx esbuild --loader:.jsx=jsx --outfile=/dev/null hvostoed.jsx`.

Проверки, которые гоняет CI (все — по данным, вырезанным из самого файла игры):
`solver.js` (геометрия, объявленный потолок и отметки звёзд), `hints.mjs`
(подсказка доводит до потолка на обоих паках), `plancheck.mjs` (игра проходит задуманный
план генератора, включая прогон «всё сразу»: тест обязан хоть раз прогнать луч
через портал, мост и поворот на одной доске, — и прогон «колючая ест последней»,
где шипы носит участница решения), `ending.mjs`
(правило конца партии против полного перебора плюс «жадность не переросла потолок»).

**Якорь может тихо сломать проверку.** `ending.mjs` резал логику от
`const facing = (cells)` — то есть без `SIDES` и `sideName`, которые лежат строкой
выше, — и упал бы на первом же уровне с поворотом. Ворота молчали только потому, что
ручных уровней с поворотами ещё нет; нашлось это случайно, когда тем же срезом мерили
сгенерированные доски. Якорь у всех проверок теперь один: `const SIDES = { n:`.

## 12a. Подсказка идёт по задуманному плану

Уровень строится ИЗ плана, и план едет в уровне (`plan` — список змей по ходам).
Подсказка сначала смотрит в него: пока игрок с плана не сошёл, ответ точен по
построению и мгновенен. Перебор (`planGoal`) остаётся только для отклонившихся и
теперь отличает «не нашёл за отведённый бюджет» от «нельзя» — раньше он возвращал
на оба случая null, и интерфейс объявлял проходимый уровень непроходимым.

Приёмка крафта перевёрнута тем же движением: вместо «пусть игра поищет решение заново»
теперь «пусть игра пройдёт задуманное». Точнее, дешевле и заодно ловит расхождение
механики игры с генератором — что `plancheck.mjs` и делает в CI.

**Смерть по массе.** Обед массу сохраняет, теряется она только на вылете, а цель не
больше стартовой массы. Значит «клеток на поле меньше цели» — точный признак проигрыша
за одно сложение. Без него правило порога позволяло расти вечно, ни разу не дорастая
до цели, и игрок ходил по мёртвому уровню, не зная об этом.

## 12b. Обмен партиями (`sharecode.mjs`, `inbox.mjs`)

Присылать надо не уровень, а ПАРТИЮ: доску целиком плюс список ходов игрока плюс за что
она прислана. Сам уровень почти ничего не говорит — важно, на каком ходу человек свернул
и что нажимал.

Доска, а не сид с конфигом: сид однозначен только при неизменном генераторе, а он
меняется каждую неделю. Двоичная упаковка держит уровень 9×9 на 11 змей в ~220 символах.
Кодек один на игру и на разбор — два экземпляра расходятся всегда.

В игре: флажок в шапке (в любой момент) и быстрые кнопки на экранах итога. Копилка
копится в мастерской, оттуда «скопировать всё» одним куском. На стороне репозитория
`node inbox.mjs файл` разбирает коды механикой, вырезанной из самой игры, и печатает,
был ли уровень проходим, на каком ходу игрок сошёл с плана и на каком ходу цель стала
недостижима.

## 13. Открытые вопросы и роадмап

Ближайшее: плейтест сложности уровней 7–10; новые уровни генератором (расширить его на валуны и колючек); звук (глоток, шлепок блока, фанфары победы) и вибрация; подсветка первого хода на уровне 1; сохранение прогресса при переносе из артефакта. Дальше: пакеты уровней по механикам, ежедневный уровень, редактор уровней на базе солвера, скины змей, упаковка в мобильное приложение (Capacitor поверх Vite — кратчайший путь). Непроверенные идеи механик: лёд-проскальзывание, змея-призрак; змея-секач (идея автора: врезавшись в бок чужого тела, разрубает её пополам — требует решения, как задаются голова и взгляд у задней половины, и правки солвера; статус — набросок). Открытые вопросы аварийной модели: нужна ли звезда «без аварий»; не сделать ли «Продолжить» платным (только «Заново»). Решено не делать: сердечки-жизни (см. §3), таймеры реального времени.

## Приложение A. Эталонная логика (нормативная)

Если правила из §2 читаются двусмысленно — истиной считается этот код (он же в игре и солвере):

```js
const facing = (cells) => [cells[0][0] - cells[1][0], cells[0][1] - cells[1][1]];

function raycast(snakes, sid, W, H, rockSet) {
  const s = snakes.find((q) => q.id === sid);
  const [dx, dy] = facing(s.cells);
  const occ = occMap(snakes);            // клетка -> {sid, ci, len, spiky}
  let [x, y] = s.cells[0];
  const gap = [];
  for (;;) {
    x += dx; y += dy;
    if (x < 0 || y < 0 || x >= W || y >= H) return { kind: "edge", gap, dir: [dx, dy] };
    if (rockSet.has(x + "," + y))          return { kind: "rock", gap };
    const hit = occ.get(x + "," + y);
    if (hit) {
      if (hit.sid === sid)                 return { kind: "self", gap };
      if (hit.ci === hit.len - 1)
        return hit.spiky ? { kind: "spikyTail", target: hit.sid, gap }
                         : { kind: "tail",      target: hit.sid, gap };
      if (hit.ci === 0)                    return { kind: "head", target: hit.sid, gap };
      return { kind: "body", target: hit.sid, gap };
    }
    gap.push([x, y]);
  }
}

// Съесть можно ТОЛЬКО kind === "tail". Выпуск — только kind === "edge".
function applyEat(snakes, eaterId, ray) {
  const prey = snakes.find((s) => s.id === ray.target);
  const food = new Set(prey.cells.map(([x, y]) => x + "," + y));
  const path = ray.gap.concat(prey.cells.slice().reverse()); // зазор + жертва от хвоста к голове
  let cells = snakes.find((s) => s.id === eaterId).cells.map((c) => c.slice());
  for (const p of path) {
    cells.unshift([p[0], p[1]]);                 // голова шагает вперёд
    if (!food.has(p[0] + "," + p[1])) cells.pop(); // хвост подтягивается только вне еды
  }
  return snakes.filter((s) => s.id !== ray.target)
               .map((s) => (s.id === eaterId ? { ...s, cells } : s));
}
```

Следствие геометрии, которое обязано сохраняться при любом рефакторинге: финальные «голова−шея» едока равны прежним «голова−шея» жертвы — **направление наследуется**.
